# SPEC-059: one link, one decision, and both players hear about it

Status: verified
Owner: agent
Created: 2026-11-11

## Problem

A link is stored symmetrically (SPEC-025: one row per pair, `low_id < high_id`),
so both players see each other's name and balance.  Everything around that row
is one-sided, though, and three defects follow from it:

1. **Two cards for one pair.**  `Bot.request_link` looks for a duplicate request
   only among *the requester's own* pending cards (`WHERE requester=?`).  If both
   players ask for each other in the same window, two cards land in the admin
   group for the same pair.  Reproduced: two pending rows, requesters 10 and 20.
2. **The second card fails with the wrong reason.**  Approving the first card
   links the pair, which changes the proposal fingerprint; the second card then
   dies in `assert_proposal_current` with «از زمان ساخت این کارت، مانده یا
   اطلاعات مرتبط تغییر کرده است؛ برای دیدن وضعیت تازه دوباره درخواست بدهید.»
   Nothing was wrong — the pair simply got linked a second earlier.
3. **Nobody is told.**  `notify_requester` only speaks for `declare_debt`, so
   after a link is approved neither the requester nor the partner receives a
   word.  A player finds out only by asking for their balance, and the partner —
   whose balance is now visible to somebody else — is never told at all.

## Goal

One pair, one pending card; a duplicate card closes with a sentence that says
what actually happened; and both players are told, in one short message each,
that the link exists.

## Scope

- `Bot.request_link`: the duplicate check covers every pending `commands` row,
  not only the requester's, so the other side cannot file the same pair.
- `Bot.confirm`: when an approved `commands` payload is a single `player_link`
  whose pair is already linked, the request is marked approved and the card is
  stamped «✅ از قبل وصل بودند» instead of failing the staleness check.  The
  after-the-fact report is skipped for that click (nothing changed).
- `Bot.close_card`: accepts an explicit status line, so a card can be closed
  with something other than «تأیید شد».
- `Bot.announce_link`: after a link is applied, each player with a known Bale
  account gets one message naming the partner and saying that either side can
  propose a settle, that no money moves by itself, and that the admin can undo
  it.

## Non-goals

- **Two-sided consent.**  The partner still does not approve the link; the admin
  does.  This specification only removes the silence, not the asymmetry of
  consent.  A partner-approval flow is a separate decision.
- No notification for `unlink`; removing a link is an admin action and stays
  quiet for now.
- No change to `shared_links`, `partner_ids`, `link_players`, the schema, or what
  a partner may see (name and balance only — never phone, receipts or history).
- No change to the approval card's text or buttons.

## Contracts

- `request_link` refuses with «درخواست پیوند این دو حساب از قبل ثبت شده و منتظر
  بررسی ادمین است.» and creates no row when any pending `commands` card already
  targets the same pair, in either order.
- `confirm` on a duplicate link card: `pending.status` becomes `approved`, the
  card loses its buttons and reads «✅ از قبل وصل بودند», and the returned text
  names both players.  It never raises.
- The duplicate branch runs **before** `assert_proposal_current`, so a real
  staleness (balance changed, TTL) is still reported for every other card.
- `announce_link` sends exactly one message per player that has `bale_id`; a
  player without a Bale account is skipped silently, and the admin still sees
  the approval.
- Nothing in this path writes to `ledger`, `receipts` or any balance.

## Acceptance Criteria

- [x] AC-001: with one request pending for a pair, a request from the other side
  is refused and the pending count stays at one.
- [x] AC-002: approving a duplicate link card closes it with the «از قبل وصل
  بودند» line, marks the request approved, and raises nothing.
- [x] AC-003: after an approval, both players receive one message naming the
  partner.
- [x] AC-004: the link is still exactly one row and both players see each other's
  name and balance.

## Safety Constraints

- A link still comes into existence only through an admin click on a card; the
  duplicate branch can close a card but never create a link by itself.
- The message to a player is generated by the bot, carries no balance, and names
  only the partner — no phone, no receipt, no ledger line.
- The financial path is untouched: no ledger row, no settle, no receipt.
- Failing to notify a player must not fail the approval; the approval is already
  committed when the messages are queued.

## Notes

- Decision: refuse the second request instead of merging the two cards.  One
  pair, one decision is easier to explain than a card that silently disappears.
- Decision: mark the duplicate as `approved` — the state the admin asked for
  holds.  The card's own line and the toast carry the nuance.
- Decision: notify after the commit, through the outbox like every other
  message, so a provider hiccup cannot undo an approval.
- Related: SPEC-025 (links), SPEC-037 (unlink and suggestion coverage),
  SPEC-043 (a requester is told), SPEC-053 (card delivery), SPEC-056 (a decided
  card is stamped).
